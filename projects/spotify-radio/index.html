01 / CONSTRAINTS

What the system had to work around

Spotify supplied playlist reads and writes, but this development-mode app did not have dependable per-track genre or audio-feature data. Spotify therefore became the source and destination layer, while Last.fm supplied community tags for tracks, albums, and artists. The tool does not download or inspect audio.

DATA ACCESS

No audio dependency

The classifier operates on metadata and tags, so it can run without storing copyrighted audio files.

DATA QUALITY

Last.fm tags are noisy

Coverage differs by song, counts are user-generated, and some tags describe fandoms rather than music.

SAFETY

The source is immutable

The source playlist ID is rejected as a publish destination. Every write goes to a generated playlist.

API LIMITS

Network calls need state

Spotify pagination, 100-item write batches, Last.fm rate limits, and retries are handled explicitly.

03 / CLASSIFIER

Track evidence is allowed to overrule the artist

The initial version treated artist genres as the main signal. That failed on artists whose catalog spans several styles. Version 4 uses an evidence hierarchy and changes the multipliers based on what is available for each individual song.

TRACK EVIDENCE AVAILABLE

1.00 track / 0.58 album / 0.14 artist

The track dominates. Album and artist tags only add context.

ALBUM EVIDENCE AVAILABLE

0.84 album / 0.24 artist

The album becomes the main signal when the track has no useful tags.

ARTIST-ONLY FALLBACK

0.72 primary artist

Artist evidence remains usable but carries less authority. Featured artists receive another 0.45 multiplier.

TAG COMBINATION

Strongest vote plus limited reinforcement

Duplicate evidence keeps its strongest weight and adds 18% of the weaker supporting vote.

Each station defines primary tags, secondary includes, exclusions, optional year ranges, and whether a primary tag is mandatory. Generic labels such as pop, rock, hip hop, and electronic receive lower multipliers, especially when they come from artist-level evidence. Exclusion weight reduces a score multiplicatively, and final scores use log1p to limit the effect of many overlapping tags.

A song is assigned only when the winning score reaches 0.19. Confidence is recorded as (winner - runner_up) / winner. The current configuration keeps one destination per track, but stores every score so overlap can be reviewed later.

06 / TRADEOFFS

Decisions that affected the result

RULE ENGINE VS. AUDIO MODEL

Deterministic metadata won

It is reproducible, cheap to rerun, and easy to inspect. It cannot detect tempo, timbre, or mood directly.

PRECISION VS. COVERAGE

Uncertain tracks stay uncertain

Required primary tags and the 0.19 floor reduce false positives but leave 233 tracks for review.

FRESHNESS VS. RATE LIMITS

Enrichment is cached

The cache contains 2,566 track, 1,986 album, and 1,609 artist records. Refreshing is explicit.

ONE STATION VS. OVERLAP

Assignments are exclusive

This avoids duplicate playlists at the cost of hiding some genuine cross-genre relationships.

The last taxonomy change split a broad pop station into Headliners and The Avenue. Removing pop rock and adult contemporary from Headliners produced a separate 127-track station without introducing overlaps.

07 / PUBLISHING

Writes are explicit and repeatable

  • Authorization Code with PKCE is used, so no Spotify client secret is stored.
  • analyze and preview are read-only; only publish writes.
  • publish --dry-run lists every intended create or update.
  • Destination IDs are persisted, so another publish updates the same playlists.
  • Track URIs are written in batches of 100 with retry handling.
  • A read-only verification pass checked all 20 remote totals: 2,604 tracks and zero mismatches.

Python 3.12, standard library HTTP, Spotify Web API, Last.fm API, OAuth PKCE, HTML, and CSS.
